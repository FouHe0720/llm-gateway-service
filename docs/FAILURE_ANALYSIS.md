# 失败案例与性能退化

依据正式 Mock `20261021T053001Z-mock-33f3d4` 与完整真实运行 `20261021T054417Z-real-bdb4f7`。
表格由 `scripts/update_benchmark_docs.py` 从原始数据生成，见 [BENCHMARK_RESULTS](BENCHMARK_RESULTS.md)。
不删除失败请求，不用 HTTP 200 替代任务正确率，不把跨轮波动改成稳定提升。

## 1. 任务路由没有优于全部 1.5B

固定 18 题 × 两轮：全 0.5B 8/36、全 1.5B 20/36、任务路由 12/36 严格匹配。
准确率分别为 22.2%、55.6%、33.3%。路由相对全 1.5B 退化，不宣称其实现智能最优选模。

该协议把提取/算术交给 0.5B、推理交给 1.5B，规则在评测前确定，但不能保证“小任务”由小模型稳定遵循格式。
失败示例：要求 `NO`，0.5B 返回 `NO.`；要求整数 `63`，返回 `The integer answer to 9 * 7 is 63.`；
部分推理输出长解释，被 64 token 上限截断。它们在既定 exact-match 协议下算错。
这说明当前指标同时测语义答案与格式遵循，不能直接将该比例解释为模型通用推理正确率。

每 18 题的模型加载耗时合计中位数：全 0.5B 2303.59ms、全 1.5B 2452.52ms、路由 25456.37ms。
4GB 策略限制一个模型驻留，任务顺序中的模型切换多次触发加载。正确任务平均耗时也从全 1.5B
298.06ms 增至路由 1206.20ms；此条件均值受到“哪些题答对/哪些题冷启动”影响，不能单独比较效用。

后续实验应保持原数据集和此基线，另建协议评估结构化输出约束、模型批次调度和更合适的路由规则。
任何规则调参需要独立开发集与未观察的评测集，不能在这 18 题上调出漂亮结果当作泛化提升。

## 2. 缓存节省调用不等于整体 P95 必然下降

真实 0.5B：90% 重复组每轮模型调用从 10 降为 1，命中率 90%，P50 从 38.63ms 降到 2.04ms；
但含一条模型 cold 请求的 N=10 样本中，nearest-rank P95 就是最大值，P95 从 2902.55ms 到 2999.56ms，
没有改善。0% 重复率组没有调用节省，其含冷启动 P95 也出现回退。

Mock 90% 重复组仍有 10% miss，P95 落在 miss 耗时区间；不能用命中率等比例推导 P95 降幅。
后续应分别看热态、冷态、命中与未命中，并扩大样本量。当前缓存无 single-flight，
不能推断并发相同 prompt 会合并成一次推理。

## 3. Retry 对永久连接失败没有恢复收益

B 热态每轮 N=100：主 endpoint 永久拒绝连接时，无恢复和 Retry 成功率均为 0%；
尝试数从 100 增为 300，P95 中位数从 11.71ms 增为 37.58ms。
只有显式配置的健康备用 endpoint 使 Retry+Fallback 达到 100%，共发起 400 次传输尝试。
这是一次可控故障场景，不说明备用真实模型具有同等答案质量。

读取超时在 Retry 组仍为 80% 成功率：这是避免盲目重复执行的策略，不是遗漏重试。
Fallback 的主上游请求即使关闭连接，也可能继续计算；网关不能保证远端停止推理或停止计费。
流开始后不重试、不回退，客户端需检查 done/error。

## 4. 高并发性能不稳定，网关有真实代价

A 配置 20ms Mock，热态并发 1 的配对 ΔP95 中位数为 3.05ms。
并发 20/50 的多轮差异明显，部分轮次甚至 Gateway 分位数低于 Direct；全部差值保留在 comparisons.csv。
不能选择一轮反向差值声称“网关加速”，也不能以这些短闭环实验推断生产吞吐。

这些实验在同一台 WSL 笔记本上运行负载发生器与两个服务，且包含日志/序列化、调度和连接池行为。
当前没有 profiler/packet capture 证实高并发回退的单一原因。默认 keep-alive 保留数 20 小于并发 50，
应作为独立变量继续测试，之后研究有界队列与事件循环/客户端负载瓶颈。

## 5. 实验台开发期错误与修正

开发期使用 Uvicorn fd= 传递 TCP socket，本机安装版该分支重建 AF_UNIX family 元信息；
发现数十毫秒传输延迟后，检查源码并改为保留 AF_INET + TCP_NODELAY + serve(sockets=[...])。
修正和连接池预热后重新采集正式三轮。原始开发记录留在本地，未作为正式发布性能结论，
也不把实验台修正产生的差值冒充 Gateway 算法优化。

截图最初缺少 libnspr4/libnss3 与中文字体，已从 Ubuntu 官方源下载并仅解包到项目 .venv，
无 sudo/系统安装。最终 Playwright 实际渲染报告并生成 PNG，JavaScript 错误数为 0。

## 6. 硬件与可推广性

正式真实运行采到整卡显存峰值 2535MiB，共 358 个有效 GPU 样本（包含 D/E/C 与其他进程）。
Ollama /api/ps 样本中，0.5B/1.5B 的 size_vram 与 size 相同，context=1024，模型均在 GPU 驻留。
本轮未观察 OOM；未运行 3B，未增加至客户端并发 4。并行推理配置为 1，因此并发 2 的 TTFT 上升主要体现排队。
采样约 500ms，可能漏掉瞬时峰值，且包含 Windows/其他进程；不能作为模型独占显存精确值。

冷启动只卸载模型，不清 OS 页缓存。两轮真实实验、18 道任务、每组 4 条 E 热请求均属小规模验证，
没有统计显著性或通用质量结论。模型标签/digest、参数和全部输出均保存，后续扩大实验时应另存新 run。
